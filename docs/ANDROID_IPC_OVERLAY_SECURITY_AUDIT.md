## Executive Summary

This security assessment audited the Android system-level attack surface of the Re:Focus application. The audit focused on inter-process communication (IPC), accessibility service binding, untrusted accessibility node tree handling, WindowManager floating overlay behavior, tapjacking/clickjacking vectors, and broadcast receiver spoofing.

The architecture demonstrates strong security hygiene in modern Android requirements (e.g., explicit immutable PendingIntents, strict `BIND_ACCESSIBILITY_SERVICE` permission enforcement, and bounded node extraction preventing memory DoS). However, specific security risks exist in dynamically registered debug broadcast receivers on legacy Android versions (pre-API 33), potential UI spoofing of accessibility trees by hostile target applications, and lifecycle synchronization when overlay permissions or accessibility privileges are revoked mid-session.

## 3. AccessibilityService Security Assessment (`ReelTrackerService`)

### A. Binding & Authorization
- **Declaration:** Declared in `AndroidManifest.xml` with `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`.
- **System Binding:** The Android OS `AccessibilityManagerService` is the only entity capable of binding to `ReelTrackerService`. Third-party applications cannot issue `startService()`, `stopService()`, or `bindService()` to this component.
- **Config XML (`accessibility_service_config.xml`):**
  - `accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged|typeViewScrolled"`
  - `accessibilityFeedbackType="feedbackGeneric"`
  - `notificationTimeout="100"`
  - `packageNames="com.instagram.android,com.google.android.youtube"`
  - `accessibilityFlags="flagDefault|flagIncludeNotImportantViews|flagRetrieveInteractiveWindows"`
  - `canRetrieveWindowContent="true"`

### B. Untrusted Input Handling (Accessibility Tree Processing)
- **Hostile Node Injection:** All node text, content descriptions, class names, view IDs, and hierarchy depth received from `AccessibilityNodeInfo` originate from third-party application processes (`com.instagram.android` and `com.google.android.youtube`).
- **Input Sanitization:**
  - `InstagramDetectorV2.kt` and `YouTubeDetector.kt` inspect node tree structures for short-form video UI patterns (Reels/Shorts containers, like buttons, author tags, share buttons).
  - **Memory DoS Defense:** Node tree traversal in BFS mode enforces `MAX_EXTRACTION_NODES = 200` and depth boundaries. Malicious apps generating infinite or deeply nested view hierarchies cannot cause an `OutOfMemoryError` or ANR in `ReelTrackerService`.
  - **Node Recycling:** Code properly invokes `recycle()` on node instances across traversal paths, preventing native memory leaks on legacy API levels.
- **Accessibility Data Leakage:**
  - `ReelTrackerService` does not extract, persist, or transmit user keystrokes, personal messages, usernames, or video content text. Only UI component structural fingerprints and count metrics are extracted.

## 4. Overlay Security Assessment (`FloatingCounterManager` & `OverlayStateManager`)

### A. WindowManager Layout Parameters
- **Overlay Type:** Uses `WindowManager.LayoutParams.TYPE_ACCESSIBILITY_OVERLAY` when running within the accessibility context, falling back to `TYPE_APPLICATION_OVERLAY` where appropriate.
- **Flags:**
  - `FLAG_NOT_FOCUSABLE`: Overlay never captures input focus, preventing keyboard interception or accessibility focus hijacking.
  - `FLAG_NOT_TOUCH_MODAL`: Touches outside the small floating pill pass directly through to the underlying application.
  - `FLAG_LAYOUT_IN_SCREEN` & `FLAG_LAYOUT_NO_LIMITS`: Coordinates window placement.
- **Dimensions & Footprint:** The floating pill is a compact `WrapContent` widget positioned at user-defined edge coordinates. It does not occupy full-screen dimensions.

### B. Tapjacking & Clickjacking Analysis
- **Interference with System UI:** `FloatingCounterManager` does not display over system permission dialogs, package installers, or device administrator prompts (`FLAG_NOT_TOUCHABLE` is dynamically applied when touch pass-through is needed).
- **Touch Interception:** Touches directly on the floating counter pill launch `MainActivity` via `context.packageManager.getLaunchIntentForPackage()`. It does not intercept underlying Instagram/YouTube video interactions, scroll gestures, or system back navigation.
- **Overlay Persistence:** `OverlayStateManager` monitors foreground package switches and window state changes. When the user exits Instagram or YouTube (switches to Home, Settings, or another app), the overlay visibility transitions to `View.GONE` / `View.INVISIBLE` via `hideOverlay()`.

## 5. BroadcastReceiver & IPC Security Assessment

### A. Dynamically Registered Receivers

#### 1. Debug Broadcast Receiver (`ReelTrackerService.kt:L248-L264`)
- **Intent Filter Actions:**
  - `com.reeltrak.app.DEBUG_INCREMENT`
  - `com.reeltrak.app.DEBUG_RESET`
  - `com.reeltrak.app.DEBUG_DESTROY`
  - `com.reeltrak.app.DEBUG_SHOW_OVERLAY`
- **Registration Flag:** Registered with `ContextCompat.RECEIVER_NOT_EXPORTED` on API 33+.
- **Vulnerability / Security Gap:**
  - On devices running **API level 32 and below**, `RECEIVER_NOT_EXPORTED` is not enforced natively by the OS platform if not backed by custom signature permissions.
  - In debug/testing builds, if this receiver remains active, any co-located application on the device can broadcast these actions to arbitrarily increment reel counters, reset tracking sessions, or force overlay display.
  - **Remediation Recommendation:** Wrap registration strictly inside `if (BuildConfig.DEBUG)` or completely eliminate runtime debug broadcast receivers in production release builds.

#### 2. Screen State Receiver (`ReelTrackerService.kt`)
- **Intent Filter Actions:**
  - `android.intent.action.SCREEN_OFF`
  - `android.intent.action.SCREEN_ON`
- **Registration Flag:** Registered with `ContextCompat.RECEIVER_EXPORTED` (Mandatory for system-broadcasted screen state events).
- **Security Posture:** Safe. The receiver only pauses/resumes tracking timers and handles no sensitive extras or IPC data.

## 8. Detailed Findings & Security Deficiencies

### Finding ID: IPC-01 — Runtime Debug Broadcast Receiver Active in Codebase
- **Severity:** `MEDIUM`
- **Component:** `com.reeltrak.app.services.ReelTrackerService`
- **Location:** `app/src/main/java/com/reeltrak/app/services/ReelTrackerService.kt#L248-L264`
- **Current Behavior:** A dynamic broadcast receiver listens for `com.reeltrak.app.DEBUG_INCREMENT`, `com.reeltrak.app.DEBUG_RESET`, and `com.reeltrak.app.DEBUG_SHOW_OVERLAY`.
- **Security Impact:** On Android 12 (API 32) and below, any local third-party app can broadcast these actions to tamper with the user's active reel counts, fake streaks, and trigger unexpected UI overlays.
- **Exploitability:** Moderate (Requires co-located app on pre-Android 13 devices or debug build variant).
- **Remediation:** Remove debug receivers from production builds using BuildConfig guards:
  ```kotlin
  if (BuildConfig.DEBUG) {
      registerDebugReceiver()
  }
  ```

---

### Finding ID: IPC-02 — Accessibility Service Lifecycle Inconsistency on Abrupt Permission Revocation
- **Severity:** `LOW`
- **Component:** `com.reeltrak.app.services.FloatingCounterManager`
- **Location:** `app/src/main/java/com/reeltrak/app/services/FloatingCounterManager.kt`
- **Current Behavior:** If the accessibility service is disabled by the user via system settings while the overlay is attached, the overlay cleanup relies on `onServiceDisconnected()` or `onDestroy()`.
- **Security Impact:** In rare OEM ROM edge cases (e.g., aggressive background kill), orphaned overlay views can remain attached until the next window manager hierarchy update.
- **Remediation:** Add defensive `runCatching` blocks and lifecycle listeners tied to `ProcessLifecycleOwner` to clean up floating windows during unexpected process state transitions.

## 9. Missing Security Controls Summary

1. **BuildConfig Guard on Diagnostic Receivers:** Debug IPC broadcast triggers lack compilation-level exclusion from release builds.
2. **Dynamic Overlay Obscurity Detection (`setFilterTouchesWhenObscured`):** Ensure all interactive elements inside `FloatingCounterManager` enforce `filterTouchesWhenObscured = true` to guard against malicious overlays positioned above Re:Focus components.
